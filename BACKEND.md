# BACKEND.md — документация Backend MedQueue KG

## 1. О проекте

**MedQueue KG** — backend для приложения записи пациентов в клиники Кыргызстана.

Основная задача backend — предоставить REST API для работы с пользователями, клиниками, врачами, расписаниями, записями пациентов и уведомлениями.

Проект рассчитан на дальнейшее расширение и совместную разработку.

---

# 2. Архитектура проекта

Backend построен на основе **Django + Django REST Framework**.

Проект разделён на несколько Django-приложений, каждое из которых отвечает за отдельную область системы.

```text
MedQueue_KG/
│
├── config/
│   ├── settings/
│   │   ├── __init__.py
│   │   ├── base.py
│   │   ├── development.py
│   │   └── production.py
│   │
│   ├── urls.py
│   ├── asgi.py
│   └── wsgi.py
│
├── users/
│
├── clinics/
│
├── appointments/
│
├── notifications/
│
├── manage.py
├── .env
├── .gitignore
├── requirements.txt
└── README.md
```

> Структура проекта может изменяться по мере развития системы.

# 4. Основные сущности

## User

Пользователь системы.

Может иметь одну из ролей:

```text
PATIENT
DOCTOR
ADMIN
```

Пользователь может иметь:

* имя;
* фамилию;
* номер телефона;
* email;
* дату рождения;
* роль;
* данные авторизации.

---

Примерные данные:

```text
name
address
description
phone
email
```

Название и описание поддерживают русский и кыргызский языки.

---

## Specialization

```text
Офтальмолог
```

Связан с:

```text

```

Возможные данные:


## Schedule

Определяет:

* начало работы;
* окончание работы;
* продолжительность одного слота;
* возможность записи.

Например:

```text

09:00 — 17:00

```

Связывает:

Основные статусы:

```text

CONFIRMED
CHECKED_IN
COMPLETED
CANCELLED
NO_SHOW
```

Примерные поля:


Типы уведомлений могут включать:

```text
APPOINTMENT_CREATED

APPOINTMENT_CANCELLED
```

# 5. Связи между сущностями

Основные отношения:

```text
User
 │
 ├── Patient
 │      └── Appointment
 │
 └── Doctor
        ├── Clinic
        ├── Specialization
        ├── Schedule
        └── Appointment
```

Более подробно:

```text
Clinic
   │
   └── Doctor
          │
          ├── Specialization
          ├── Schedule
          └── Appointment
                    │
                    └── Patient (User)
```

Один пациент может иметь много записей.

Один врач может иметь много записей.

Один врач может иметь несколько элементов расписания.

Одна клиника может содержать нескольких врачей.

# 6. Аутентификация

Для авторизации используется **JWT**.

Основные endpoints:

```http
POST /api/auth/register/
POST /api/auth/login/
POST /api/auth/refresh/
GET  /api/auth/me/
PATCH /api/auth/me/
```

После успешной авторизации клиент получает:

```text
access token
refresh token
```

Access token используется для доступа к защищённым endpoint'ам.

# 7. Permissions

Доступ к API зависит от роли пользователя.

Пример:

### Patient

Может:

* просматривать клиники;
* просматривать врачей;
* просматривать расписание;
* получать свободные слоты;
* создавать собственные записи;
* отменять собственные записи;
* выполнять check-in;
* просматривать свои уведомления.

### Doctor

Может:

* просматривать свои записи;
* управлять своим расписанием;
* получать информацию о пациентах, записанных к нему;
* получать уведомления.

### Admin

Может:

* управлять клиниками;
* управлять врачами;
* управлять специализациями;
* управлять расписаниями;
* управлять пользователями;
* управлять записями.

# 8. Система доступных слотов

Свободные слоты не хранятся как отдельные записи в базе данных.

Они **генерируются на основе расписания врача**.

Например:

```text
Schedule:

09:00 — 13:00
slot duration = 30 min
```

Backend генерирует:

```text
09:00
09:30
10:00
10:30
11:00
11:30
12:00
12:30
```

После этого из списка удаляются уже занятые слоты.

В результате клиент получает только доступное время.

---

# 9. Защита от двойного бронирования

Система должна гарантировать, что два пациента не смогут одновременно забронировать один и тот же слот.

Для этого используются:

* проверки доступности;
* database constraints;
* transactions;
* `transaction.atomic()`.

Проверка на уровне Python недостаточна, поскольку два запроса могут прийти практически одновременно.

Поэтому защита должна существовать и на уровне базы данных.

# 10. Статусы Appointment

Жизненный цикл записи:

```text
BOOKED
   ↓
CONFIRMED
   ↓
CHECKED_IN
   ↓
COMPLETED
```

Также запись может перейти в:

```text
CANCELLED
NO_SHOW
```

Конкретные правила перехода между статусами должны быть определены в business logic.

---

# 11. Check-in

После прихода пациента в клинику он может выполнить check-in.

При успешном check-in:

```text
Appointment.status = CHECKED_IN
```

Также может сохраняться:

```text
check_in_at
```

В дальнейшем check-in может быть расширен QR-кодом или другим способом подтверждения присутствия.

---

# 12. Уведомления

Система должна создавать уведомления при важных событиях.

Например:

```text
Patient booked an appointment
        ↓
Notification created
        ↓
Patient receives notification
```

В дальнейшем для автоматических напоминаний может использоваться:

```text
Celery + Redis
```

Например:

```text
Appointment tomorrow
        ↓
Celery task
        ↓
Reminder notification
```

# 13. Локализация

Проект поддерживает два языка:

```text
ru — Русский
ky — Кыргызча
```

Используются два подхода.

### Django i18n

Используется для системных сообщений и интерфейсных строк.

### django-modeltranslation

Используется для контента, который хранится в базе данных.

Например:

```text
Clinic.name
    name_ru
    name_ky
```

или

```text
Specialization.name
    name_ru
    name_ky
```

# 15. Business Logic

Бизнес-логика не должна полностью находиться внутри views.

При усложнении проекта рекомендуется выносить сложную логику в отдельные сервисы или функции.

Например:

```text
appointments/
├── models.py
├── serializers.py
├── views.py
├── urls.py
├── permissions.py
├── services.py
└── tests.py
```

`services.py` может отвечать за такие операции, как:

```text
create_appointment()
cancel_appointment()
generate_available_slots()
check_in_patient()
```

# 19. Безопасность

Основные правила:

* секретные ключи не хранятся в Git;
* API защищается JWT;
* используются permissions;
* пользователь не должен иметь доступ к чужим записям;
* необходимо валидировать входные данные;
* важные ограничения должны дублироваться на уровне базы данных;
* production должен работать с `DEBUG=False`.

# 22. Git Workflow

Для совместной разработки рекомендуется использовать отдельные ветки.

Например:

```text

```

Основная разработка выполняется не напрямую в `main`, а через feature-ветки и Pull Request.

Пример:

```bash

```

После завершения работы:

```text
feature/appointments
        ↓
Pull Request
        ↓
Code Review
        ↓
```

# 24. Что пока не входит в MVP

Следующие функции не являются частью первоначальной версии:

* онлайн-оплата;
* медицинские карты;
* хранение медицинской истории;
* видеоконсультации;
* встроенный чат;
* интеграция с государственными системами;
* полноценная система отзывов;
* сложная геолокация;
* медицинская диагностика с помощью AI.

Эти функции могут рассматриваться в будущих версиях проекта.
